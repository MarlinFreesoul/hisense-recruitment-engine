# 4.1 Spec Kit Lite 权威描述

> 一句话总结：求证「Spec Kit Lite」并非 GitHub 官方产品，锁定官方 shorter path + OpenSpec 为权威锚点。
> 所属轮次：R4 ｜ 来源：WebSearch + Exa + Metaso 三引擎并行

## 结论先行

**「Spec Kit Lite」没有官方产品**——GitHub 官方仓库与文档中不存在叫这个名字的工具或命令。我在 R3 用的「Spec-Kit-Lite」是**我的自造推荐词**，不是既成标准。诚实做法：把它**重新锚定到官方出处**——

1. **官方权威锚点**：Spec Kit 官方文档的 **shorter/smaller-feature path**（`/speckit.specify → plan → tasks → implement`，跳过 clarify/analyze/constitution 质量门）。这是「轻量 Spec Kit」的**官方表述**。
2. **社区最权威的"更轻"替代**：**OpenSpec**（42K+ star，定位「比 Spec Kit 更轻，但比 IDE 简单 Plan 更有结构」）。
3. **社区 lite 分支**：SpecLite CLI（"Spec Kit 的务实演进"）、LeanSpec 等。

## ② 权重与矩阵逻辑

**问题**：哪个是「Spec Kit Lite」最权威的描述？（权重 = 官方性 50% + 可执行性 30% + 社区采用度 20%）

| 候选 | 官方性(5) | 可执行(3) | 采用度(2) | 加权总分 |
|------|:---:|:---:|:---:|:---:|
| Spec Kit 官方 shorter path | 10 | 9 | 8 | **9.3** |
| OpenSpec | 6 | 9 | 9 | **7.5** |
| SpecLite CLI | 2 | 8 | 5 | **4.4** |
| LeanSpec | 2 | 7 | 3 | **3.7** |

**结论**：官方 shorter path 是「轻量 Spec Kit」的最权威描述（9.3），OpenSpec 是"想要现成更轻工具"时的首选实现（7.5）。

## ③ 对抗性辩证矩阵

| 命题 | 正方（For） | 反方（Against） | 化解（Resolution） |
|------|------|------|------|
| 存在官方 "Spec Kit Lite" | R3 报告用了 "Spec-Kit-Lite"；社区有多个 lite 实现，说明需求真实 | GitHub 官方无此产品/命令；官方只有 "shorter path" 说法 | "Spec Kit Lite" 作为**品牌名**不存在，作为**方法论**有官方出处（shorter path） |
| 项目应继续用 "Spec Kit Lite" 命名 | 简洁、已写入 R3 报告 | 会误导为官方标准 | 保留命名，但在 MAPBOARD 明确其 = 官方 shorter path 的轻量实践 |
| 用 OpenSpec 替换 Spec Kit | 更轻、42K star | 需换脚手架，中途迁移成本高 | 保留 Spec Kit 脚手架，取其 shorter path 理念即可 |

## 落点

本项目「Spec Kit Lite」的**权威定义**写死为：

> **Spec Kit 官方 shorter path 的轻量实践**：`specify → plan → tasks → implement` 四步，砍掉 clarify/analyze/constitution 质量门；外加本项目的**四要素报告规范**（信源评分 + 权重矩阵 + 对抗辩证 + 角色分工）与**地图板溯源**。
