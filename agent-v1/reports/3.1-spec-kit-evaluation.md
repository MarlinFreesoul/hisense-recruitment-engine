# Spec Kit 适用性评估（黑客松语境）

> 问题：Spec Kit 是否适用于当前黑客松项目？当"实战落地解决方案交付"时是否可行？有无更优推荐？
> 结论先行：**全量 Spec Kit = 不可行（对 24h 黑客松是"高射炮打蚊子"）；推荐「Spec-Kit-Lite」（保留 spec-first 思维 + Claude Code Plan Mode，砍掉仪式）**。评分系统与举证见下。

## 一、Spec Kit 是什么（事实，供举证）

- GitHub 开源（MIT）的 **Spec-Driven Development（SDD）** 工具，2025 年末开源，至 2026 年 6 月 **11.8万+ star**（[GitHub 官方仓库](https://github.com/github/spec-kit)、[官方文档](https://github.github.io/spec-kit/)）。
- 工作流：**Constitution → Specify → Clarify → Plan → Tasks → Analyze → Implement**，7 个 slash 命令（`/speckit.specify` 等）。
- 产出 `.specify/` 目录：`memory/constitution.md` + `specs/[feature]/`（spec.md / plan.md / tasks.md / data-model.md）。
- 支持 Claude Code、Copilot、Gemini、Cursor 等 **30+ AI agent**（无锁定）。
- 核心哲学：**"先定义 what，再谈 how"**，spec 是"可执行的规格"，直接驱动实现。

## 二、Spec Kit 的已知局限（举证，采自多位实践者）

| 局限 | 证据 | 来源 |
|------|------|------|
| **"一套工作流打天下"，小任务过重** | "用小钢炮砸核桃（sledgehammer to crack a nut）"；无轻量路径 | Birgitta Böckeler 评述（[Fontoura 实践者指南](https://felipefontoura.com/articles/github-spec-kit/)） |
| **无机器可读的审批门** | 无 `.status` token，推进与否靠人自律 | 同上 |
| **artifact 量过大** | 每 feature 6+ 个 markdown，冗长重复，"一堵 markdown 墙" | 同上 |
| **20-40% 额外 token 开销** | agent 每轮重读 spec/plan/tasks | [Fundesk 指南](https://www.fundesk.io/spec-driven-development-github-spec-kit-guide) |
| **不适合快速原型/探索** | "原型用 vibe，生产才 SDD"；"throwaway 代码别写 spec" | 同上 + [Kanani](https://erfan-kanani.com/blog/spec-kit) |
| **SDD 不适用于"创造性探索"阶段** | 官方明确三阶段：0-to-1 / 创造性探索 / 迭代增强；SDD 只覆盖首尾，不覆盖探索 | [Spec Kit 官方文档](https://github.github.io/spec-kit/concepts/sdd.html) |
| **学习曲线 + 首跑慢** | "前几轮比预期慢" | [Endapally](https://arunendapally.com/posts/spec-driven-development-with-spec-kit/) |

## 三、评分系统

**评分维度（按黑客松语境加权）**：

| 维度 | 权重 | 理由 |
|------|------|------|
| 时间到 Demo | 30% | 24h 内交付是第一约束 |
| Demo/路演质量 | 25% | 评委只看 demo + 讲的故事 |
| 工程能力信号（阳谋） | 15% | 向海信 scouts 展示"不是 vibe coder" |
| 团队协同（4人） | 15% | spec 是共享事实源 |
| 零数据冷启动适配 | 10% | "无业务数据"是核心约束 |
| 可维护/可追溯 | 5% | throwaway demo 最不重要 |

**五方案评分（1-10）**：

| 方案 | 时间到Demo | Demo质量 | 工程信号 | 团队协同 | 零数据 | 可维护 | **加权总分** |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| A. 全量 Spec Kit | 3 | 5 | 10 | 8 | 3 | 10 | **5.65** |
| B. **Spec-Kit-Lite**（推荐） | 7 | 8 | 8 | 7 | 8 | 7 | **7.50** |
| C. 纯 Vibe/Demo-first | 10 | 8 | 3 | 4 | 6 | 2 | **6.75** |
| D. AWS Kiro | 5 | 6 | 8 | 7 | 6 | 8 | **6.15** |
| E. Claude Code Plan Mode | 9 | 7 | 6 | 5 | 7 | 4 | **7.00** |

**关键读数**：
1. **全量 Spec Kit 得分最低（5.65）**——时间成本（学习曲线 + 20-40% token + artifact 评审）在 24h 约束下被 30% 权重放大，且 SDD 本就不适用于"创造性探索"（零数据场景恰是探索）。
2. **纯 vibe 反而高于全量 Spec Kit（6.75 > 5.65）**——但工程信号仅 3 分，会毁掉"阳谋"（向海信证明执行力）。
3. **Spec-Kit-Lite 最优（7.50）**——保留 spec-first 的工程信号 + 零数据适配，砍掉仪式，正好打中"阳谋"要害。

## 四、结论与推荐

**判定**：
- **作为"24h 黑客松的构建流程"**：全量 Spec Kit **不可行**（时间不够、场景错配——零数据是探索不是 0-to-1）。
- **作为"实战落地解决方案交付"**：Spec Kit **可行但非最优**。它的价值（可追溯、正确性）在 demo 评审中几乎不可见；评委看的是 demo + 故事，不是你的 constitution.md。
- **真正的杠杆**：Spec Kit 的 **spec-first 思维**本身是对的——它生成的 `spec.md`/`plan.md`/`tasks.md` 恰好能**直接当路演材料**（展示"我有清晰的产品定义 + 技术设计 + 任务拆解"），这比堆代码更能向海信证明能力。

**推荐（已量化）**：**B「Spec-Kit-Lite」= 保留已建好的 `.specify/` 脚手架 + 写一份高质量 spec.md/plan.md/tasks.md 作为交付物 + 用 Claude Code Plan Mode 做审批门，实现时走快循环。** 即"**start vibe, finish spec-driven**"（业界共识，见 Fundesk/Kanani）。

**落地建议**：
1. 不跑全量 7 命令，只走 `specify → plan → tasks` 三步产出三份 markdown（已在 repo 里），实现用 Plan Mode 逐任务快跑。
2. 把 `spec.md` 当作**产品路演脚本**写：用户故事 + 验收标准 + 显式 out-of-scope（最被低估但最有价值的一段）。
3. `constitution.md` 保留但只写 3-5 条硬约束（如"AI 只辅助不替代决策""零数据可冷启动"），当作答辩的"设计原则"陈述。

**备选（若需要更轻）**：E「Claude Code Plan Mode」是"80/20 版"，零安装、自带审批门，适合连 spec 文件都不想要的极限提速场景；但缺少持久化 spec 交付物，工程信号弱于 B。
